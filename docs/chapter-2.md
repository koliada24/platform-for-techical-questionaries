# Розділ 2. Аналіз мов програмування, технологій розроблення веб-додатків та способів інтеграції інструментів для написання коду та створення діаграм

## 2.1. Загальні архітектурні передумови

Розроблюваний веб-застосунок — платформа для створення та проведення технічних опитувальників з інтеграцією Google Classroom — висуває такий набір нефункціональних вимог, які напряму впливають на вибір технологічного стеку:

- **Інтерактивний клієнт.** Викладач конструює тест із різнотипними питаннями (вибір однієї відповіді, кількох, текст, код, діаграма), студент проходить тест із вбудованими редактором коду та редактором діаграм. Це потребує rich-UI з реактивним станом, тому застосовано підхід **Single-Page Application (SPA)** з рендерингом на стороні клієнта.
- **Контрольоване виконання коду.** Відповіді типу «код» потрібно компілювати й виконувати з обмеженням за часом, що накладає вимогу на наявність вбудованого виконавця у мові серверної частини.
- **Інтеграція з Google Classroom.** Обов'язкові потоки OAuth 2.0, виклики Classroom REST API, збереження refresh-токенів — це вимагає зрілої інфраструктури аутентифікації на бекенді.
- **Гетерогенність відповідей.** Малі структуровані дані (текст, варіанти) логічно зберігати в реляційній СУБД, а великі бінарні артефакти (код, файли діаграм Excalidraw) — окремо у блоковому сховищі.
- **Відтворюваність розгортання.** Дипломне рішення має запускатися однією командою на будь-якій машині — звідси контейнеризація.

Усі подальші рішення мотивуються відповідністю саме цим вимогам.

## 2.2. Серверна частина

### 2.2.1. Вибір мови програмування — C# / .NET 10

Серверну частину реалізовано на мові **C#** з використанням платформи **.NET 10** і фреймворку **ASP.NET Core**. Розгляньмо ключові альтернативи й аргументацію вибору.

| Критерій | C# / .NET 10 | Java / Spring Boot | Node.js / Express | Python / Django |
|---|---|---|---|---|
| Продуктивність HTTP | Дуже висока (Kestrel — один із лідерів TechEmpower) | Висока | Середня | Низька–середня |
| Статична типізація | Так, з nullable-аналізом | Так | Лише через TypeScript | Лише через type hints |
| Виконання довільного коду в процесі | **Roslyn Scripting** з коробки | Janino / GraalVM (складніше) | `eval` / `vm` (небезпечно) | `exec` (небезпечно) |
| Інтеграція з OAuth/Identity | Вбудована (`Microsoft.AspNetCore.Authentication.*`, Identity) | Spring Security | Сторонні модулі | django-allauth |
| EF-сумісний ORM | EF Core (LINQ, JSON-колонки, owned types) | Hibernate / JPA | Prisma / TypeORM | Django ORM / SQLAlchemy |

**Обґрунтування вибору C# / .NET 10:**

1. **Roslyn Scripting** (`Microsoft.CodeAnalysis.CSharp.Scripting`) — критичний фактор. Він дозволяє виконувати C#-код студента **в межах того самого процесу API**, з повною типізацією, контролем `using`-неймспейсів і таймаутом. Це усуває потребу в окремому контейнері-«пісочниці», що було б обов'язковим, наприклад, для Node.js (`vm` не є безпечною ізоляцією) чи Python (`exec` ще менш безпечний).
2. **Зрілий стек аутентифікації.** Пакети `Microsoft.AspNetCore.Authentication.Google` і `Microsoft.AspNetCore.Identity.EntityFrameworkCore` забезпечують декларативну реєстрацію OAuth-схем (у проєкті використано **дві іменовані схеми** — `Google-Teacher` і `Google-Student` — з різними scope'ами Classroom і окремими external-cookie). Аналог у Node.js (`passport-google-oauth20`) працює, але потребує більше «glue code».
3. **Nullable reference types** (`<Nullable>enable</Nullable>`) — забезпечує перевірку null-безпечності на етапі компіляції, що зменшує клас runtime-помилок без необхідності окремого TypeScript-подібного шару.
4. **Продуктивність.** Kestrel + .NET 10 показують вищі показники RPS, ніж Node.js та Python-фреймворки на тих самих сценаріях за бенчмарками TechEmpower.
5. **Кросплатформність.** .NET 10 виконується на Linux, що робить тривіальною контейнеризацію в офіційному `mcr.microsoft.com/dotnet/aspnet:10.0` образі.

### 2.2.2. ASP.NET Core (контролерний підхід)

Обрано саме **класичний контролерний підхід** (`AddControllers`), а не Minimal APIs:

- Контролери (`AuthController`, `TestTemplatesController`, `PublishedTestsController`, `TestsInProgressController`, `ClassroomController`, `CodeRunController`, `LspController`) забезпечують **природну ієрархічну організацію за ресурсами**, зрозумілу читачу-промоутеру/комісії.
- Атрибути `[Authorize(Roles = "Teacher")]` / `[Authorize(Roles = "Student")]` декларативно виражають політику доступу; у Minimal APIs це робиться менш виразно.

### 2.2.3. ORM — Entity Framework Core 10 + Npgsql

| Альтернатива | Переваги | Недоліки |
|---|---|---|
| **EF Core 10 (вибрано)** | LINQ-запити з статичною перевіркою; підтримка JSON-колонок (owned types через `ToJson()`); спадкоємці через TPH-дискримінатор; інтеграція з ASP.NET Core Identity | Дещо повільніше за Dapper на масивних читаннях |
| Dapper | Максимальна швидкість | Низькорівневий, без міграцій і моделювання |
| NHibernate | Зрілий | Морально застарілий, погано інтегрується з .NET 10 |

Конкретні переваги EF Core у цьому проєкті, видимі в `AppDbContext`:

- **Дискримінаторне успадкування** для `AnswerInProgress` / `AnswerSubmitted` дозволило природно змоделювати поліморфізм відповідей (Single, Multiple, Text, Code, Diagram) у єдиній таблиці без втрати типобезпеки.
- **`OwnsMany(...).ToJson()`** для варіантів відповіді (`Answers` всередині `QuestionTemplate` / `PublishedQuestion`) — дозволяє зберігати малі вкладені колекції як JSON-стовпець у PostgreSQL без зайвої таблиці-зв'язки.
- **`HasIndex` + `IsUnique`** забезпечує реляційні інваріанти на рівні БД (наприклад, унікальність пари `(StudentId, PublishedTestId)` для активної спроби).

### 2.2.4. ASP.NET Core Identity

Замість самописної автентифікації використано **`IdentityCore<ApplicationUser>` + `IdentityRole`**. Локальний пароль явно вимкнено — застосунок автентифікує лише через Google. Identity використовується як стандартизоване сховище користувачів і ролей, що дає:

- Готову нормалізовану модель користувача (`AspNetUsers`, `AspNetRoles`, `AspNetUserRoles`) і відповідні таблиці у PostgreSQL.
- Ролі `Teacher` / `Student` як claim-и в cookie `qapp.auth`, що використовуються `[Authorize(Roles=...)]`.

## 2.3. Клієнтська частина

### 2.3.1. Мова — TypeScript

Замість «чистого» JavaScript обрано **TypeScript ~6.0** з таких міркувань:

- **Статична перевірка типів** на стадії збірки усуває цілий клас помилок «cannot read property … of undefined» і робить рефакторинг безпечним.
- **Узгоджені DTO між клієнтом і сервером.** Контракти з `Api/Contracts/*` віддзеркалюються в `Client/src/types/*` як `interface`/`type`, що гарантує сумісність.
- **Інструментальна підтримка** (автодоповнення, переходи до визначення, перейменування) у IDE значно вища за чистий JS.

### 2.3.2. UI-фреймворк — React 19

Розглянуті альтернативи: Angular, Vue, Svelte.

| Критерій | React 19 (вибрано) | Angular | Vue | Svelte |
|---|---|---|---|---|
| Розмір екосистеми | Найбільший | Великий | Великий | Середній |
| Поріг входу | Низький | Високий (DI, RxJS, decorators) | Середній | Низький |
| Інтеграція з Monaco / Excalidraw | Готові обгортки | Менш зріла | Менш зріла | Обмежена |
| Hooks і функціональні компоненти | Так | Декларативно через сервіси | Composition API | Реактивні присвоєння |

Вирішальним стало **наявність якісних React-обгорток для двох ключових інтеграцій**: `@monaco-editor/react` (редактор коду) і `@excalidraw/excalidraw` (редактор діаграм) — обидва офіційно підтримуються саме як React-пакети. Запит на віджети рівня IDE робить React природним вибором.

### 2.3.3. Збірник — Vite 8

Альтернативи — Webpack, Parcel, Turbopack.

- **Vite** використовує нативні ES-модулі під час розробки, що дає **миттєвий dev-server та HMR** навіть на великих проєктах.
- На етапі продакшен-білду Vite використовує Rollup, який створює оптимізований tree-shaken bundle.
- Webpack функціонально співмірний, але повільніший на cold-start і вимагає значно більше конфігурування.

### 2.3.4. UI-бібліотека — React-Bootstrap 2 + Bootstrap 5

Розглядалися Material UI, Ant Design, Mantine.

- **Bootstrap 5** дає звичну, перевірену часом, доступну (a11y) систему компонентів і утилітних класів. Команда (один розробник у дипломному проєкті) знайома з Bootstrap, що зменшує час на стилізацію.
- **React-Bootstrap** надає компоненти-обгортки (`Modal`, `Form`, `Navbar`, `Card`), що інтегруються з React-станом без `jQuery`.
- Material UI / Ant Design — потужніші, але мають значно більший bundle size і більш інвазивний design language, що зайве для дипломного скоупу.

### 2.3.5. Робота з формами — React Hook Form

Альтернативи: Formik, контрольовані компоненти власноруч, redux-form.

- **React Hook Form** мінімізує ре-рендери (поле не викликає рендер усієї форми завдяки `register`/`uncontrolled` підходу).
- Підтримка `useFieldArray` критична для конструктора тестів, де викладач динамічно додає/видаляє питання та варіанти відповідей.
- Менший bundle і менше boilerplate порівняно з Formik.

### 2.3.6. HTTP-клієнт — Axios

- Уніфікована інстанція `api` (з `withCredentials: true` і `baseURL`) задається один раз — далі всі модулі (`api/attempts.ts`, `api/publishedTests.ts`, `api/testTemplates.ts`) користуються нею.
- Інтерсептори дозволяють централізовано обробляти 401/403 (вихід з сесії).
- Альтернатива — нативний `fetch` — потребує власних обгорток для серіалізації, помилок і credentials, тому Axios зменшує boilerplate.

### 2.3.7. Маршрутизація — React Router DOM 7

Стандарт de-facto для маршрутизації у React-SPA. Підтримує вкладені маршрути, лоадери, захищені маршрути (для розділення публічної сторінки логіну, кабінету викладача, сторінки спроби студента та сторінки відправленої роботи).

## 2.4. Інтеграція інструментів для написання коду

### 2.4.1. Редактор коду — Monaco Editor

Для текстових полів типу «відповідь у вигляді коду» потрібен повноцінний редактор з підсвіткою синтаксису, автодоповненням і підтримкою клавіатурних скорочень рівня IDE. Розглянуті альтернативи:

| Редактор | Переваги | Недоліки |
|---|---|---|
| **Monaco Editor (вибрано)** | Той самий редактор, що у VS Code; вбудовані LSP-протокол, IntelliSense, дебагер, мульти-курсор; широка підтримка мов | Вагомий bundle (~2 МБ) |
| CodeMirror 6 | Менший bundle, модульний | Менш «IDE-подібний», слабша готова підтримка LSP |
| Ace | Простий | Морально застарілий, обмежений |

**Monaco** обрано саме через **сумісність з LSP**: редактор у браузері спілкується з мовним сервером, отримуючи реальні підказки компілятора, а не статичні regex-евристики.

### 2.4.2. Виконання C#-коду — Roslyn Scripting

Сервіс `CSharpCodeRunner` (`Api/Services/CodeRunner/`) використовує `Microsoft.CodeAnalysis.CSharp.Scripting` для **запуску фрагмента коду в межах процесу API**. Розглянуті альтернативи:

| Підхід | Переваги | Недоліки |
|---|---|---|
| **Roslyn Scripting (вибрано)** | Запуск in-process, без зовнішніх контейнерів; повний доступ до .NET BCL; точні діагностики компілятора | Не є sandbox'ом — обмежено через wall-clock timeout |
| Окремий Docker-контейнер на запит | Сильна ізоляція | Висока латентність; складність оркестрації |
| `dotnet-script` як окремий процес | Простота | Вища латентність холодного старту |

У дипломному скоупі прийнятним компромісом є **wall-clock-таймаут** як одиничний механізм захисту, із чітким зазначенням у тексті роботи, що для production-середовища необхідна додаткова ізоляція (cgroups, gVisor, Firecracker).

### 2.4.3. Language Server Protocol — `csharp-ls` через WebSocket-міст

Щоб у редакторі Monaco відображались **реальні** підказки C#-компілятора (а не regex-евристики), реалізовано **LSP-міст**:

- На клієнті — кастомна обгортка (`Client/src/lsp/csharpLsp.ts`), яка з'єднує Monaco з WebSocket-каналом `/api/lsp` (контролер `LspController`).
- На сервері контролер запускає окремий процес `csharp-ls` (Language Server для C#) і **проксіює JSON-RPC повідомлення** між WebSocket-сесією браузера й stdio мовного сервера.
- Альтернатива — повністю клієнтський OmniSharp — нереалістична через те, що C#-аналіз неможливо ефективно запустити повністю в браузері.

Такий підхід дозволяє студенту бачити **ті самі помилки компілятора, що побачить серверний `CSharpCodeRunner`** під час перевірки, що покращує дидактичну якість тесту.

## 2.5. Інтеграція інструменту для створення діаграм

Для відповідей типу «діаграма» інтегровано бібліотеку **Excalidraw** (`@excalidraw/excalidraw`).

| Бібліотека | Переваги | Недоліки |
|---|---|---|
| **Excalidraw (вибрано)** | Готова React-компонента; «hand-drawn» стиль, зручний для UML/схем рівня курсу; експорт у власний JSON та PNG/SVG; open-source MIT | Не є строго UML-валідатором |
| `mxgraph` / draw.io embed | Більше «корпоративних» фігур | Складніший в інтеграції, важчий bundle |
| `joint.js` / `mermaid` | Хороші для генерованих діаграм | Менш зручні як **редактори** на полотні |

Excalidraw повертає JSON-сцену, яку клієнт серіалізує і **завантажує до S3-сумісного сховища MinIO** (див. 2.6.4) — у БД зберігається лише ключ об'єкта (`ObjectKey`). Це робить схему БД легкою і не змішує реляційні дані з блобами.

## 2.6. Інфраструктура та зберігання даних

### 2.6.1. СУБД — PostgreSQL 17

Альтернативи: MySQL/MariaDB, MS SQL Server, SQLite.

| Критерій | PostgreSQL 17 | MySQL 8 | SQL Server | SQLite |
|---|---|---|---|---|
| Open-source | Так | Так | Ні | Так |
| JSON-колонки (`jsonb`) | Дуже зрілі | Базові | Так | Лише як TEXT |
| EF Core-провайдер (`Npgsql`) | Зрілий, активний | Менш зрілий | Офіційний | Офіційний |
| Підходить для багатокористувацького production | Так | Так | Так | **Ні** (один writer) |

**Обґрунтування:**

- **PostgreSQL** обрано як стандарт open-source реляційних СУБД зі зрілими `jsonb`-колонками, які EF Core 10 використовує для `OwnsMany().ToJson()` (варіанти відповідей).
- **SQLite** використовувався на ранніх етапах розробки як файлова БД для швидкого старту, але не підходить для production через обмежений конкурентний доступ (одночасно лише один писач).
- **MS SQL Server** ліцензійний, що суперечить вимозі вільного розгортання дипломного рішення.

### 2.6.2. Об'єктне сховище — MinIO (S3-сумісне)

Великі артефакти відповідей (відправлений код, JSON Excalidraw-сцен) зберігаються **поза реляційною БД**, у MinIO.

| Підхід | Переваги | Недоліки |
|---|---|---|
| **MinIO (вибрано)** | S3-сумісний API; легко локально розгортається через Docker; той самий клієнт працює з AWS S3 у production | Потребує окремого сервісу |
| Зберігання як `bytea` у PostgreSQL | Простота | Роздуває БД, погіршує бекапи, неефективно для великих об'єктів |
| Файлова система контейнера API | Простота | Втрата даних при перезапуску, неможливість горизонтального масштабування |

S3-сумісний інтерфейс важливий, бо в production-розгортанні MinIO можна тривіально замінити на AWS S3 / Backblaze B2 / Wasabi без зміни коду — `MinioObjectStorageService` залежить лише від інтерфейсу `IMinioClient`, який реалізує S3-протокол.

### 2.6.3. Контейнеризація — Docker + Docker Compose

Усі компоненти (`qapp-api`, `qapp-client`, `qapp-db`, `qapp-minio`) запаковані в окремі контейнери і оркеструються через `docker-compose.yml`. Альтернативами були:

- **Чисте розгортання на хост-машині** — порушує ізоляцію залежностей (PostgreSQL, MinIO), не дає відтворюваності.
- **Kubernetes** — надмірний для дипломного скоупу.

Docker Compose забезпечує:

- **Health-checks** (`pg_isready`, `minio/health/live`) і **залежності між сервісами** (`depends_on: condition: service_healthy`) — API не стартує, доки БД не готова.
- **Іменовані volumes** (`db-data`, `minio-data`) для збереження стану між перезапусками.
- **Одну команду `docker compose up`** — критично для презентації роботи.

### 2.6.4. Веб-сервер для SPA — Nginx

Скомпільований Vite-бандл (`dist/`) розміщується в контейнері з **Nginx** (`Client/Dockerfile`, `nginx.conf`).

- Nginx — індустріальний стандарт для віддачі статичного контенту з мінімальним споживанням пам'яті.
- Конфігурація використовує SPA-fallback (`try_files $uri /index.html;`), необхідний для роботи клієнтського React Router.
- Альтернатива (запуск Vite-dev-server у production) — недопустима, бо це інструмент розробки, не оптимізований для прод-навантаження.

## 2.7. Інтеграція з Google Classroom

Зовнішня інтеграція реалізована через **OAuth 2.0** (`Microsoft.AspNetCore.Authentication.Google`) і прямі HTTPS-виклики **Google Classroom REST API** через типізований `HttpClient` (`GoogleClassroomClient`).

Особливості реалізації:

- **Дві іменовані OAuth-схеми** — `Google-Teacher` і `Google-Student` — з різними наборами scope'ів. Викладач отримує `classroom.courses.readonly`, `classroom.rosters.readonly`, `classroom.coursework.students`; студент — лише `classroom.courses.readonly`, `classroom.coursework.me`. Це втілює принцип **мінімальних привілеїв**.
- **Окремі external-cookie** (`External-Teacher`, `External-Student`) використовуються тимчасово під час OAuth-callback, ізолюючи зовнішню тимчасову ідентичність від основної сесії застосунку (`qapp.auth`).
- **Збереження refresh-токенів** (`SaveTokens = true`, `AccessType = "offline"`) у полях `ApplicationUser` дозволяє API звертатися до Classroom API від імені користувача й тоді, коли його активної сесії в браузері немає (наприклад, для відкладеної синхронізації оцінок).

Розгляду альтернатив (пряма інтеграція з LMS-альтернативами Moodle, Canvas) в роботі не проводиться, оскільки Google Classroom є цільовою платформою інтеграції за умовами ТЗ.

## 2.8. Інструменти забезпечення якості коду

- **ESLint 10** + **typescript-eslint** — статичний аналіз клієнтського коду; підключений плагін `react-hooks` гарантує дотримання правил React Hooks.
- **TypeScript Compiler** (`tsc -b`) — у скрипті `build` виконується перед `vite build`, що блокує деплой при наявності помилок типів.
- **Nullable reference types** і **`ImplicitUsings`** на рівні `Api.csproj` — компіляторна підтримка null-безпечності й чистоти `using`-директив.

Ці інструменти не потребують додаткового виконавчого середовища і запускаються в межах тих самих контейнерів, що й застосунок.

## 2.9. Висновки до розділу

Підсумовуючи, обраний технологічний стек:

- **Бекенд:** C# 12 / .NET 10, ASP.NET Core (контролерний підхід), EF Core 10 з провайдером Npgsql, ASP.NET Core Identity, Roslyn Scripting, Google OAuth + Classroom API, MinIO .NET SDK.
- **Фронтенд:** TypeScript ~6.0, React 19, Vite 8, React Router 7, React-Bootstrap 2, React Hook Form, Axios, Monaco Editor, Excalidraw.
- **Інфраструктура:** PostgreSQL 17, MinIO (S3-сумісне), Nginx, Docker + Docker Compose.

Кожен компонент обрано не за принципом «модно/новітньо», а через конкретну функціональну вимогу, яку він закриває:
- **Roslyn Scripting** — єдиний прагматичний спосіб виконати C#-код студента в межах процесу;
- **Monaco + LSP-міст** — єдина зріла комбінація, що дає підказки реального компілятора в браузері;
- **Excalidraw** — найзручніший готовий React-редактор довільних діаграм;
- **PostgreSQL `jsonb` + EF Core `ToJson()`** — баланс між нормалізацією та простотою для вкладених варіантів відповідей;
- **MinIO** — економно розділяє реляційні дані та бінарні артефакти зі збереженням сумісності з AWS S3;
- **Docker Compose** — забезпечує відтворюване розгортання для захисту дипломної роботи.

Запропонована комбінація утворює цілісну, послідовну архітектуру, що задовольняє всі функціональні та нефункціональні вимоги, поставлені в Розділі 1.
